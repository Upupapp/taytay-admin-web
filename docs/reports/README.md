# Reports, analytics and exports

Figures for planning and accountability, exposing as little about individual
residents as the work allows.

Built in TAB 19. Decision records: `DL-104` … `DL-108`.

---

## Aggregate first

Fourteen reports. **Thirteen are counts.** One names people, and it has to argue
for itself (`DL-104`).

A person-level report carries three things an aggregate one does not:

1. **A stated reason** — `personLevelJustification`, required on person-level
   and forbidden on aggregate. "We have always shown names here" is not a lawful
   basis; writing the reason down is what makes it reviewable.
2. **A higher permission** — `report.export`, not `report.view`. Naming people
   is a different act from reading a count of them.
3. **A caution on screen** — it says it names people and must not be circulated.

`reportProblems` refuses a definition that breaks any of those, and
`check:reports` fails the build if the person-level count grows.

The one report that qualifies is **data completeness**, and its reason is
concrete: it exists to be worked through record by record, and "42 records
incomplete" cannot be acted on because nobody knows which 42.

The catalogue is **data**, like programme eligibility (`DL-66`). Adding a report
is a record in `REPORT_CATALOGUE` plus a producer in the adapter — never a new
screen, and never a new `@if`. No component branches on a report id.

## An aggregate is not automatically anonymous

> Barangay San Juan: 1 VAWC survivor served.

That names somebody to anyone in that barangay who knows who has been to the
office. Two is barely better. A table of counts can identify a person as surely
as a list of names, and the office would have published it believing it had
published statistics.

So counts of **people or households** below `SMALL_CELL_THRESHOLD` are withheld.
Four choices inside that rule are deliberate (`DL-105`):

| Choice | Why |
| --- | --- |
| **Withheld, not dropped** | A missing row reads as "none" — a different and false claim. The row keeps its label and is marked. |
| **Not rounded** | Rounding 2 up to 5 puts a figure in a report that is not true, and somebody will act on it. |
| **Never zero** | Zero identifies nobody. Hiding it hides the absence of service, which is the finding a planning report most needs. |
| **Drill-down removed** | Withholding a figure but linking to the four records behind it withholds nothing. |

The **total is taken before suppression** and labelled as such, because the
alternative is a reader adding up the visible rows and quietly believing a
smaller number. The notice sits **above** the table, not in a footnote.

Series counting *things* — documents, requests, releases — are not suppressed. A
count of vouchers identifies nobody, and suppressing it would cost the report
its usefulness for no privacy gain. The caller states which kind it is
(`aboutPeople` vs `aboutCases`) rather than the code guessing.

### The threshold is unconfirmed, and says so

Five follows common statistical disclosure practice for small-area counts. **No
Taytay issuance was supplied fixing it**, so it is marked
`convention-pending-confirmation` and the report screen prints the basis —
exactly as the intake review windows do (`DL-68`).

**There is no way to ask for the unsuppressed set.** No port parameter, no
adapter flag, no screen toggle. "Just this once" is how a threshold stops being
one.

## Charts are tables

`ChartTable` — built in TAB 06 — is a real `<table>` with a caption, a header row
and one row per category. The bar is an `aria-hidden` span that only repeats what
the number beside it already says.

TAB 19 **extends it rather than adding a charting library** (`DL-108`). That
satisfies all three of the master command's accessibility asks at once: summary
text, a tabular equivalent, and nothing conveyed by hue alone.

`ReportSeries.summary` is **required**, not optional. It names the largest row
and its share — a claim a reader can verify against the row beneath it — rather
than describing a shape. An optional field is one that is eventually omitted,
and a chart plus a separate accessible table is two things that drift apart.

`check:reports` fails the build on a `<canvas>` or `<svg>` in a report template,
on a chart rendered without its summary bound, and on any charting dependency in
`package.json`.

## Exports carry their own conditions

A spreadsheet on somebody's desktop six months from now has no screen around it.
A printed report that does not say what it covers **will** be read as covering
everything.

Every export begins with a manifest, **in the file** (`DL-106`):

```
Report,"Social welfare caseload"
Question,"How many cases is the office carrying, and in what state?"
Filter applied,"Last 30 days · Barangay: San Juan"
Generated at,"2026-08-16T02:00:00.000Z"
Generated by,"Teodoro Lim"
Rows,6
Names individuals,"No"
Handling,"…protected under RA 10173. Keep it within the office…"
```

The file is **composed by the data layer**, never assembled by a screen — the
same rule as the payout manifest (`DL-92`) and the referral summary (`DL-82`).
A template holding the fuller result is one binding away from writing a name
into a spreadsheet the report was never meant to contain. The checker fails the
build if a screen touches `csvCell`, a `Blob` or `URL.createObjectURL`.

A **person-level export is warned about before the file exists**, not after it
is on somebody's desktop. The warning says plainly that nothing can be recalled.

## Staff workload is not a ranking

The master command asks for staff workload reporting and warns, in the same
line, against simplistic performance ranking. Both halves are honoured
(`DL-107`).

The report counts **open items per officer**, so a supervisor can move work.
There is no completion rate, no average turnaround, no score and no index — and
the rows are ordered **alphabetically**. Sorting by count is what turns a
workload table into a league table, whatever the heading says.

The caution is rendered above the figures: *a heavy caseload is usually a hard
caseload, and the office cannot see from a count who is doing well.*

Same framing as the team queue (`DL-97`), which sorts by who is most behind **in
order to direct help**.

## Cautions

Four reports carry a caution above their figures, because the numbers invite a
wrong reading:

| Report | What it says |
| --- | --- |
| Staff workload | Not a productivity measure |
| Case aging | Waiting time, not lateness — no service standard has been adopted (`DL-101`) |
| Vulnerability indicators | Evidence a caseworker reads, never a decision (`DL-42`) |
| Repeat assistance | A household returning is a fact about their circumstances; it decides nobody's eligibility |
| Data completeness | Names people; do not circulate outside the office |

## Access

| Act | Permission |
| --- | --- |
| Open the hub | `report.view` |
| Open a report | `report.view` **and** the report's own permission |
| Export any report | `report.export` |
| Staff workload | `staff.view` |
| Release status | `release.view` |
| Referral outcomes | `referral.view` |
| Data completeness | `report.export` |

Each report carries its own permission on top of the module's, so the hub shows
only what an account could actually open, and `run` refuses the rest — not-found
and not-yours read identically (`DL-31`). Barangay scope is applied to every
producer.
